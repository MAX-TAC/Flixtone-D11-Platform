# Версионирование: схема для проекта

Дата: 2026-11-25.

## 1. Почему сейчас путаница

В APK сейчас:
- `versionCode` = 41 (число, которое проверяет Android при обновлении)
- имя артефакта содержит «v41» — это **только метка файла**, не версия

**Приписка в названии файла ничего не значит для Android.** Если `versionCode` не
увеличился, система откажется ставить обновление поверх равной версии.

## 2. Как надо

Два независимых поля:

| Поле | Назначение | Правило |
|---|---|---|
| `versionCode` | для Android, только целое | **всегда растёт**, никогда не уменьшается |
| `versionName` | для человека | схема `X.Y` |

### Предлагаемая схема

| Событие | versionName | versionCode |
|---|---|---|
| Первый релиз после стабилизации | `2.0` | `200` |
| Мелкие исправления | `2.1`, `2.2` | `201`, `202` |
| Крупные изменения | `3.0` | `300` |
| Экспериментальные сборки | `2.1-rc1` | `291` |

**Почему versionCode с шагом 100:** запас на 99 мелких правок внутри одной
крупной версии. `2.0`=200…299, `3.0`=300…399.

**Почему не сбрасывать в 1:** стоковый APK имеет `versionCode=1`, но мы уже
уходили на 41. Откат вниз сломает установку обновлением. Начинаем с 200.

## 3. Что делать с «v41» в истории

- Старые артефакты `v41-*` остаются как есть (история).
- Новые сборки: `versionName=2.0`, `versionCode=200`, артефакт
  `tvsettingsplus-8054-2.0-mainsettings`.
- В журнале указать: «v41 = последняя экспериментальная, 2.0 = первый
  стабильный кандидат».

## 4. Где менять

В workflow `build-tvsettingsplus-8054-audit.yml` есть вызов
`compose_brightness_v3_apk.py --version-code N`. Значение берётся оттуда.
`versionName` задаётся там же (сейчас зашит `1.0` — это тоже надо править).

**Правило на будущее:** каждое изменение кода → `versionCode += 1` минимум.
